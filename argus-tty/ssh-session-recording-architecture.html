Why SSH Session Recording Is Split Across Three Privilege-Separated Processes

Recording a session, uploading it, and emailing about it sound like one job. argus-tty deliberately gives each one its own process, running as a different identity — and the reason is the same reason you wouldn't want one process doing all three in the first place.

Three helpers, three identities

A session touches three distinct pieces of sensitive material: the transcript itself, an AWS credential to ship that transcript to S3, and an SMTP password to email about it. argus-tty runs a separate helper for each, and only one of them ever runs as root:

  • argus-tty-wrapper — runs as whichever developer, admin, or deployer just connected. It's what sshd's ForceCommand actually invokes; it records the full TTY transcript via script and the command history to /var/log/argus-tty/sessions/. It never talks to AWS or SMTP at all.
  • argus-tty-finalize — also runs as the connecting user's own uid, not root. It handles the best-effort immediate upload to S3 at logout, authenticating via the instance's IAM role. Because it runs unprivileged, a compromised developer account can see its own session files (expected — it generated them) but has no broader access as a side effect of upload happening at all.
  • argus-tty-mailer — the only one of the three that runs as root, driven by a systemd timer every 30 seconds. It's also the only process on the box that ever reads /etc/argus-tty/smtp-credentials.env (600, root-only). The wrapper never reads that file — it just queues a small local file describing the notification, an instant, network-free write, and lets the mailer pick it up later.

The effect: a developer or admin session — including a fully unrestricted admin one — never runs in a process that has read access to the SMTP password, because that process doesn't run as root and never has access to the file. Splitting the mailer out isn't about trusting admins less; it's that "the session-handling code never has the credential" is a strictly stronger guarantee than "the session-handling code is trusted not to leak the credential."

Why ForceCommand can't be skipped

Every onboarded account still owns a normal ~/.ssh/authorized_keys file — that's how their key authenticates at all. What stops someone from adding their own command="..." prefix to a key entry and skipping the recorder entirely is ordering, not a filesystem permission: OpenSSH evaluates a Match block's ForceCommand directive in sshd_config after authentication succeeds, and a ForceCommand set inside a Match block always overrides any command= restriction a user's own authorized_keys entry tries to set. The user-level file still controls things like IP restriction (from="...", see argus-tty's own allow-ip subcommand) — it just never gets the final word on what command actually runs. That's a property of sshd itself, not something argus-tty's configuration could accidentally leave a gap in, which is also why the Match Group developer,admin,deployer block applies identically to admins: more privilege doesn't buy an exemption from the same mechanism.

Why an IAM instance role, not per-account credentials

argus-tty-finalize runs as whichever account is currently connected — that's the whole point of attributing an upload to the session that produced it — which means it needs AWS credentials that resolve the same way for every current and future account, not just whichever one an admin happened to run aws configure on. A personal ~/.aws/credentials file only ever authenticates the one Linux account it's written into; it does nothing for any other developer, admin, or deployer account, and a file left in one account's home directory actually takes priority over an instance role for that one account specifically — so a stale per-user workaround can silently mask the real fix.

The mechanism that actually satisfies "every account, no per-account setup" is an EC2 instance role, attached once at the AWS account level, outside the box entirely. Every account resolves the same role automatically via the instance metadata service — nothing to configure per developer, and nothing that needs redoing when a new one is onboarded. If argus-tty status reports no usable credentials, that's almost always a missing instance role, not a missing per-user config file. When an instance role genuinely isn't an option — most commonly a cross-account bucket — argus-tty's documented fallback is one shared, group-readable credentials file every account is pointed at via /etc/environment, which is explicitly a trade-off (one static credential shared across accounts) rather than a free alternative; see the README's own treatment of that fallback for the specifics.

Non-blocking by construction, not by convention

None of this is allowed to put a login session on the hook for a network call. The immediate S3 upload attempt runs fully detached (nohup + setsid, with a hard timeout ceiling) specifically so it can't hold a session's connection open at logout, and a separate argus-tty-s3-sync.timer sweeps every two minutes, completely decoupled from any live session, to pick up anything the fast path missed — it only ever touches a session's files once the wrapper has marked them finished. Email is just a local file write on the wrapper's side; the mailer's own retry loop (every 30 seconds, up to five attempts) is what actually gets it delivered. If the aws CLI isn't installed, no credentials resolve, or SMTP is unreachable, each helper detects that up front and logs a warning via logger -t argus-tty instead of erroring — session recording to local disk always happens regardless of whether either integration is even configured.
