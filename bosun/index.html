Rails deployment for a shared host, multiple developers, zero shared secrets.

Bosun is a .deb-packaged CLI for deploying Rails apps on argus-tty-managed Ubuntu hosts — tiered developer/deployer/admin Linux accounts, a git deploy key shared across the team instead of everyone's personal key, and app secrets locked to a single unprivileged service account, not a shared group.

Launchpad PPA .deb package argus-tty recommended MIT licensed GitHub

The problem bosun actually solves isn't "how do I deploy Rails" — every tool answers that. It's "how do five developers deploy the same box without all sharing root, a personal SSH key, or read access to DATABASE_URL." Bosun provisions each app with its own ACL-locked shared/.env (root + a single service account only, not the group every developer is in), a shared per-app git deploy key instead of N personal keys, and require_role() checks on every subcommand that reuse argus-tty's existing sudoers whitelist — no new sudo privileges are ever granted to deploy an app. 

sudo add-apt-repository ppa:yadavramlaxman/argus-tty && sudo add-apt-repository ppa:yadavramlaxman/bosun
sudo apt update && sudo apt install argus-tty bosun   # or the .deb package — see Installing below
sudo bosun bootstrap                                  # one time per host: RVM multi-user

Full install guide, including the .deb-package alternative and verifying the install: Installing.

No argus-tty? Skip the first line — bosun falls back to a single-operator standalone mode automatically: no tiers, no separate service account, one account does everything. A deliberately reduced security posture for one person on their own box, not a lighter-weight substitute for argus-tty on a shared one. 

sudo bosun add myapp              # provision /var/www/myapp (admin, one time)
bosun install myapp               # ruby/gemset + OS build deps (developer/admin)
bosun setup myapp                 # releases/shared/config tree (developer/admin)
bosun deploy myapp main           # clone, build, symlink, restart, rollback-on-fail (deployer/admin)

What it does

  • Tiered Linux accounts, not one shared deploy user — argus-tty's developer/deployer/admin tiers, enforced per-subcommand by require_role(): a plain developer can't deploy; a plain deployer can't open a Rails console or read secrets.
  • Secrets locked to one service account — shared/.env is root:root 600 with a single named-user ACL grant for webapp-svc, not the shared webapps group — a compromised developer/deployer account has no standing read access to DATABASE_URL/SECRET_KEY_BASE at all.
  • One shared git deploy key per app — not N personal SSH keys to whitelist (and revoke) on the git host; distributed automatically to every current admin/deployer account.
  • Deploy with automatic rollback — clone → bundle install → assets:precompile (elevated to webapp-svc just for that one step, so the deploying account never needs standing secret access) → symlink swap → restart → health check → automatic rollback to the previous release on failure → old-release cleanup.
  • Fully overridable per app — copy do-release.sample, edit it: real bash, not a hook/plugin DSL, for a different worker (a sneakers consumer instead of Sidekiq, Docker instead of systemd, extra build steps) — every other app on the box keeps the default untouched. See adding a custom service.

How it compares

Capistrano, Mina, and Kamal all answer "clone, build, symlink, restart" well — that's not where bosun differs. None of the three has a concept of tiered Linux accounts or ACL-locked secrets at all: they assume one deploy identity (a shared SSH key, a CI token) with full access to everything the deploy needs, because they're solving the deploy choreography, not who-on-the-team-can-touch-what on a box several people share.
